# Unreleased — IR-00 runtime contracts

`docs/RELEASE-0.2.0.md` is history. This file accumulates what the NEXT lockstep bump ships; it carries no version number, because the version is chosen when the release is cut and writing one here early is how a document starts describing a state nobody decided on.

**Breaking: run events are v4.** `@getsimpledirect/vinci-run-events` adds 24 event types (`run.stalled`, `run.attempt_started`, the four `agent.turn_*`/`agent.compaction_*`/`agent.retry_*` pairs, five `tool.*`, three `governor.lease_*`, `artifact.persisted`, `artifact.verified`, `approval.expired`, `context.loaded`, `context.invalidated`, `capability.attested`, `capability.refused`, `steer.received`), two OPTIONAL `run.completed` fields (`outcome` from `RUN_OUTCOMES`, `tierReached` from `TERMINAL_TIERS`), and one OPTIONAL field on the existing v3 type `run.created`: **`workOrderDigest`** (`kind: "digest"`), which is how a consuming registry binds a run to the work order it executes.

The break is the version, not the shapes: no v3 type is removed and no existing v3 field or payload rule changed. `run.created` gains an optional field — additive within the type, and still a version bump, because a validator with `unknownFields: "reject"` does not tolerate a field it has not been told about. See C18 in `docs/conflict-register.md` for why the digest is OPTIONAL on the event while `VinciRun` requires it. `RUN_EVENT_SCHEMA_META.compatibility` is `frozen` and `unknownFields` is `reject`, so **a v4 validator REFUSES a v3 event on `schemaVersion` and does not up-convert it**, and a v3 validator refuses every v4 event. Producers and consumers of one run's log must therefore move together.

**New package `@getsimpledirect/vinci-run`** (layer 3). Six schemas, each with `validate*`, a digest over the canonical encoding of the VALIDATED value, and a `SchemaMeta`: `VinciAgent`, `VinciEnvironment`, `VinciRun`, `ContextManifest`, `HarnessAttestation` (schema version 2; the other five are version 1), `HumanCorrection`. Plus `projectRunState(events)` (a pure projection from the event log; TERMINAL is absorbing and a later event is reported, not folded away), `terminalEvidenceMissing(events)`, and `attestedHarnessCapabilities(attestation, now)`.

**Extended `HARNESS_CAPABILITIES`** in `@getsimpledirect/vinci-model-classes`, from three members to the vocabulary a governed run can actually attest (`workspace_read`, `shell_execution`, `github_publish_pr`, … ). `matchEndpointToRole` still withholds eligibility for a role requiring a harness capability until a caller passes `attestedHarnessCapabilities`; that list counts an entry only when its self-test PASSED **on an artifact whose identity is bound**, the attestation has not expired, and the id is a member of the vocabulary. Empty is the fail-closed answer, never a grant.

**`HarnessAttestation` is schema version 2** — the one schema in the package that is not v1, and the reason is a guard that refused only the honest case. v1's `observedEntrypoint` was `installed_worker | source_checkout` and only the first counted. But production workers run the daemon from `/opt/vinci-code-cli`, a root-owned git checkout deployed by `git fetch` + `git checkout --detach <sha>` + a systemd restart, and the release repository has no worker packaging path at all — so **no production worker could ever be attested** and every advanced role stayed `unevaluable [harness_capabilities_unverified]` permanently, which is the exact verdict the attestation exists to clear. Nothing checked how the bytes arrived, so the rule stopped no determined actor and reliably stopped the compliant one.

v2 replaces the delivery axis with an identity one: `installed_package | pinned_checkout | working_tree`. A `pinned_checkout` is attestable but must carry `checkoutPin: { commitId, treeId }` — the 40-hex commit and the 40-hex `git write-tree` observed there; a `pinned_checkout` without it is refused with `missing_checkout_pin`, and a pin on any other entrypoint with `checkout_pin_not_applicable`. A `working_tree` is never attestable.

**What `checkoutPin` is, stated plainly.** It is an OUT-OF-BAND DEPLOYMENT ATTESTATION that the contract records and CANNOT VERIFY. An earlier draft of this note claimed the pin was falsifiable by anyone; it is not, and that claim is withdrawn. The validator checks shape only: a `treeId` equal to the `commitId` (impossible in git), the all-zero object id, and invented 40-hex ids are all accepted and all grant the capability, and the `installed_package` arm carries no evidence field at all. Recomputing `git rev-parse <commitId>^{tree}` is available to anyone holding the repository — including an attester whose tree is dirty — so it distinguishes an honest dirty reporter from an honest clean one and constrains a dishonest one not at all. The pair is still worth recording, because named objects give a later investigation something to reconcile against the deployment record; it is not a proof. The axis change from delivery to identity stands on its own: it is the change that made a production worker attestable at all. **A v2 validator refuses a v1 attestation on `schemaVersion` and does not up-convert it**: `source_checkout` maps to `pinned_checkout` or `working_tree` depending on evidence v1 never carried, so the harness re-attests.

**Cross-language vectors.** `packages/run/vectors/` pins canonical bytes and digests for nine fixtures (including `harness-attestation-3-pinned-checkout` and `harness-attestation-4-working-tree`), with the digests pinned a second time as literals in both test files so a regeneration is a deliberate act, checked from TypeScript (`src/vectors.test.ts`) and from Python (`python/test_run_vectors.py`, reusing the one shared canonicalizer). `run-events-v4-additions.json` pins one accepted and one refused payload for each of the 24 new types. `npm run test:vectors` and `npm run gate` run both suites.

**Consumers that must move:**
- `vinci-gpu-control` — the run registry writes run events; it must move to `schemaVersion: 4` in the same change that adopts the new types, and can then persist `VinciRun` and project state from the log rather than from its own table. **The field this move exists to hand it is `run.created.workOrderDigest`**: the registry binds every Run to the work order it executes and previously could not say so in a `run.created` at all. It is optional on the event and REQUIRED on `VinciRun` — see C18.
- `vinci-code-cli` (worker) — emits the `agent.*`, `tool.*` and `context.*` events, and is what a `HarnessAttestation` names. As deployed today it is a `pinned_checkout`: it must record the 40-hex commit it was `checkout --detach`ed to (the value it already announces as `worker_build`) and the `git write-tree` of the tree it ran the self-test on. A capability observed on a `working_tree` establishes nothing.

Release mechanics unchanged: lockstep versions across every package, tag on the merged head, `release.yml` publishes on the tag.
